# 压缩包构建与交付

目标是用户能下载、解压和使用交付物。仅在云环境创建文件不算完成交付。

## 检查与构建

1. 先检查仓库说明、AGENTS.md、已有打包脚本、工作区变更、目标安装器要求及授权范围。优先复用已有脚本；不要覆盖配置或用户文件。
2. 明确 ZIP 顶层目录结构、必需元数据、运行依赖及目标平台。AstrBot 插件与 meme_manager 表情包是不同的安装入口；分别校验 metadata.yaml 与 manifest.json 等要求。
3. 使用显式文件白名单打包。排除凭据、聊天记录、数据库、缓存、虚拟环境、Git 元数据和测试替身。第三方素材必须有再分发授权。
4. 构建前执行与变更相关的测试。区分单元测试、协议检查、真实安装与实际平台收发测试；未执行的检查不得声称通过。
5. 同样输入生成相同 ZIP：固定文件顺序、时间戳和权限，保留二进制数据。可使用附带脚本；它不替代项目特有的协议或安装检查。

示例（路径相对 source，显式列举文件）：

```bash
python .agents/skills/package-delivery/scripts/build_zip.py --source . --output /tmp/example-1.0.zip main.py metadata.yaml requirements.txt
```

## 校验与交付

- 检查 ZIP CRC、无绝对路径或 `..`、无重复条目、必需文件存在；生成相邻 `.sha256` 文件。必要时在临时目录解压并执行安装器相关检查。
- 优先使用平台正式支持的附件交付能力；只有实际上传成功后才能提供附件链接。
- 若用户已授权发布到 GitHub，可复用适当仓库的独立分支、Release 或受控构件。尊重仓库可见性，不把私有内容公开，不随意新建公开仓库，不改写 main。不要自动创建无关历史的分支；先沿用现有合适的交付渠道。
- 如果没有已授权可用的发布渠道，先完成本地包与检查，再说明需要的交付渠道。不要把 `/workspace/...`、`/tmp/...`、localhost 或虚构的 sandbox 链接当作外部下载地址。
- 上传后实际 GET 下载链接：检查最终 HTTP 状态、解析 ZIP、校验 CRC 和必需元数据，并比较远程文件与本地文件的 SHA-256。HTTP 200 可能是登录页面，不能仅以状态码判定成功。保留 TLS 校验。
- 原始下载 URL、GitHub 文件页和源码分支 URL 用途不同。标明插件安装入口与手动上传方式。私有仓库/构件需登录，必须说明；不要通过删除认证绕过权限。
- 下载失败时先诊断内部路径、权限、链接类型、过期附件或网络问题。不要重复发送同一未验证地址。

## 最终回复

给出一个推荐安装/下载入口及必要操作，简述已验证结果及未验证范围。只在实际验证后声称“可下载”。本地安装 skill 不意味着所有未来会话自动拥有它：需将本目录安装到运行环境识别的 skills 目录，或置于后续仓库 `.agents/skills/package-delivery/`。
